# 0006. データソースを `SiteSource` インターフェースの背後に置く

## 状態

採用

## 文脈

[ADR 0001](0001-cosense-api-knowledge-confined-to-core.md) は「Cosense の知識を `core` に閉じ込める」
という約束だが、当初はパイプライン側が Cosense 由来の生ページを受け取り、記法パースを自分で
呼び出していた。つまり `core` の**内側**で境界が漏れており、「取得」は差し替えられても
「本文の解釈」は Cosense 前提のままだった。

この状態では、別のソース（esa、Notion など）を足そうとした瞬間にパイプラインの分岐が増える。

## 決定

`packages/core/src/source/types.ts` の `SiteSource` インターフェースに、取得だけでなく
**正規化（`normalize`）まで**含める。

- `list()` — ページ参照の列挙
- `fetch(ref)` — 1 ページの本文取得。上流で消えていたら `null`（呼び出し側はスキップ）
- `siteIcon?()` — ソース自身のアイコン（favicon の既定値）。任意。失敗しても例外にしない
- `normalize(raw)` — 生ページ → 中間モデル。**本文の記法パースはここで行う**

パイプラインは取得結果に `normalize` を map するだけで、ソースの本文フォーマットを知らない。

## 影響

- 「Cosense の知識は `source/cosense/` の中だけ」が実装として成立する（文書上の約束ではなくなる）。
- 新しいソースは `SiteSource` を実装すれば足り、パイプラインに分岐が増えない。
- `fetch` が `null` を返す設計により、list と fetch の間で削除されたページがビルドを落とさない。
  同様に `siteIcon` は失敗しても `null` を返す契約で、アイコン取得の失敗がビルドを止めない。
- 現時点で実装は Cosense のみ。抽象の妥当性は 2 つ目のソースを実装するまで検証されない
  （抽象が早すぎた場合はこの ADR を見直す）。
