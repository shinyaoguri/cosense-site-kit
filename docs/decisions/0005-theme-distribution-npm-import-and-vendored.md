# 0005. テーマは npm import と vendored の 2 モードで配布する

## 状態

採用

## 文脈

テーマ利用者の要求は二極化する。

- **早く立ち上げて本体の改善に追従したい**（個人サイト・研究室サイトの多く）
- **デザインを本格的に作り込みたい**（`.astro` を直接書き換えたい）

前者だけを想定してパッケージ配布に寄せると、作り込みたい人がテーマを fork するしかなくなる。
後者だけを想定してテンプレートのコピー配布に寄せると、大多数がテーマの改善を受け取れないまま
古いコピーを抱え続ける。

## 決定

`theme-default` は**同じパッケージで 2 モードを両立**させる。

1. **npm import（既定）** — `@cosense-site-kit/theme-default` を import すると、ルート・テンプレート・
   スタイルはパッケージが提供する。見た目の調整は `themeDefault({ ... })` のオプション、`preset`
   （CSS 変数）、`.site` の `theme.skin` で行う。改善は `npm update` で届く
2. **vendored（手動）** — パッケージが同梱する生の `.astro`（`src/`）を利用者のリポジトリにコピーし、
   `astro.config.ts` から参照する。編集は自由になるが `npm update` の追従からは外れる

`cosense.config.ts` と `.site` はどちらのモードでも共通で、npm import → vendored の移行を片道で行える。

## 影響

- テーマパッケージは `dist` だけでなく生の `src/` も同梱する必要がある（配布サイズが増える）。
- vendored した fork はフレームワークの配線を取りこぼしやすい。実際に `#no-date` の尊重や
  大文字小文字を無視したタグ判定の取りこぼしが実運用で発生した（#126）。この構造的な弱点への対策
  （高レベルコンポーネント化）は未着手で、[docs/roadmap.md](../roadmap.md) に置く。
- スキン（`preset`）は「構造は同じで配色だけ違う」需要を npm import 側で吸収するために存在する。
  構造から違うテーマは別パッケージにする。
